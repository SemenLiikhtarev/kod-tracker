ТЕХНИЧЕСКОЕ ЗАДАНИЕ (ТЗ)
На разработку системы управления проектами «КОД» (Конвейер Обработки Данных)
Версия документа: 1.0 (Финальная)
Название продукта: КОД (Конвейер Обработки Данных)
Целевая аудитория: Руководители проектов, аналитики, операторы данных (Исполнители).
1. Общие положения и цели
«КОД» — это веб-приложение (дашборд) для отслеживания и управления последовательной обработкой данных. Система работает по принципу конвейера: задачи передаются от одного исполнителя к другому.
Ключевая особенность: Файлы не хранятся в БД приложения, а физически находятся на Яндекс.Диске. Входящие заказы парсятся из Яндекс.Почты, а финальные результаты отправляются обратно через Яндекс.Почту.
2. Архитектура и Интеграции
Система состоит из Backend (API, бизнес-логика, фоновые задачи), Frontend (UI/UX) и реляционной БД.
Внешние интеграции (API):
Яндекс.Почта (IMAP / SMTP / API):
Входящие: Фоновый парсинг писем с заказами, скачивание вложений.
Исходящие: Формирование и отправка финального письма с заключением и ссылками/файлами.
Яндекс.Диск (WebDAV / REST API):
Автоматическое создание древовидной структуры папок для каждого проекта.
Перемещение файлов между папками этапов.
Генерация публичных/приватных ссылок для скачивания.
Telegram Bot API: Отправка push-уведомлений исполнителям о новых задачах и дедлайнах.
3. Ролевая модель и права доступа
Авторизация через корпоративный Яндекс ID (SSO).
Роль
Права и возможности
Руководитель
Полный доступ. Создание проектов, настройка шаблонов этапов, назначение исполнителей, принудительный сброс «захвата» задачи, финальная отправка результата клиенту. Просмотр аналитики.
Исполнитель
Видит все проекты. Может брать в работу и завершать только те этапы, которые соответствуют его «Типу обработки данных» (навыку).
Наблюдатель
Доступ только на чтение (просмотр статусов, таймлайнов и файлов).
4. Бизнес-логика: Механика «Конвейера» и «Захвата»
4.1. Инициация проекта
На корпоративную Яндекс.Почту приходит письмо с темой/шаблоном «Новый заказ».
Фоновый скрипт (Celery/Worker) парсит письмо, скачивает вложения.
Система создает карточку проекта в БД и структуру папок на Яндекс.Диске: КОД / [Номер]_[Клиент] / Этап 1 / ....
Файлы загружаются в папку Этап 1.
4.2. Механика «Захвата» (Бронирование задачи)
Чтобы исключить дублирование работы, каждый этап внутри проекта имеет статус:
🟡 Ожидает (Доступно): Видно всем исполнителям нужной роли. Кнопка «Взять в работу».
🔵 В работе (Захвачено): Исполнитель нажал «Взять в работу». В БД фиксируется executor_id. Для других сотрудников кнопка блокируется, отображается текст «Занято: [ФИО]».
🟢 Завершено: Исполнитель нажал «Завершить этап». Файлы автоматически копируются/перемещаются в папку следующего этапа на Яндекс.Диске. Следующий этап переходит в статус «Ожидает».
Защита от зависания: Руководитель или сам исполнитель могут нажать «Вернуть в пул» (снять захват), если задача не выполняется.
4.3. Финализация
На последнем этапе формируется документ «Заключение». Руководитель проверяет данные и нажимает «Отправить клиенту». Система собирает файлы с Яндекс.Диска и отправляет их через Яндекс.Почту.
5. Требования к UI/UX и Дизайн-системе
5.1. Цветовая палитра (Строгий корпоративный стиль)
Интерфейс должен быть чистым, минималистичным, не отвлекающим от данных.
Основной фон: Белый (#FFFFFF) и очень светло-серый для карточек (#F8F9FA).
Акцентный цвет (Primary): Глубокий синий (#005EB8 или #1E3A8A). Используется для главных кнопок («Взять в работу», «Завершить»), активных вкладок, ссылок.
Вторичный синий (Light Blue): (#E6F0FA). Используется для фона выделенных строк, бейджей, ховер-эффектов.
Текст: Темно-серый (#212529) для основного, серый (#6C757D) для второстепенного.
Семантические цвета: Зеленый (#198754) - Успех/Завершено; Желтый (#FFC107) - Дедлайн близко; Красный (#DC3545) - Просрочено/Ошибка.

5.3. Ключевые экраны
Дашборд «Мои задачи» (Для исполнителя):
Две вкладки: «В работе» (захваченные мной) и «Пул задач» (доступные для захвата).
Карточки задач с указанием Проекта, Текущего этапа, Дедлайна и кнопки действия.
Канбан-доска / Таймлайн (Для Руководителя):
Визуализация всех проектов. Колонки = Этапы конвейера.
Цветовая индикация дедлайнов (зеленый/желтый/красный).
Карточка проекта (Детальный вид):
Метаданные проекта.
Таймлайн этапов (с аватарками исполнителей, которые взяли этапы).
Блок «Файлы»: подтягивает список файлов из папки текущего этапа на Яндекс.Диске (через API).

7. Модель данных (Базовая структура БД)
Разработчикам необходимо реализовать следующие сущности:
Users: id, yandex_id, name, email, role, processing_types (JSON/Array).
Projects: id, client_name, yandex_folder_id, status, created_at, final_deadline.
Stages (Templates): id, name, order_index, default_deadline_hours, required_processing_type.
Tasks (Instances): id, project_id, stage_id, status (pending, in_progress, done), executor_id, taken_at, deadline_at.
Logs: id, user_id, task_id, action, timestamp (для аудита).
8. Нефункциональные требования
Конкурентный доступ (Concurrency): При нажатии «Взять в работу» использовать транзакции БД (Pessimistic Locking / SELECT ... FOR UPDATE), чтобы два пользователя не могли захватить одну задачу одновременно.
Отказоустойчивость интеграций: Если Яндекс.Диск или Почта недоступны, система не должна падать. Операции с файлами и почтой должны ставиться в очередь (Message Queue, например, RabbitMQ/Redis) и ретраиться (повторяться) до успешного выполнения.
Безопасность: Токены доступа к Яндекс API (OAuth) должны храниться в зашифрованном виде (например, в Vault или зашифрованными переменными окружения), а не в открытом виде в БД.
Адаптивность: Интерфейс должен корректно отображаться на десктопах (основной рабочий инструмент) и планшетах. Мобильная версия не обязательна, но Telegram-бот должен полностью дублировать функционал уведомлений и принятия задач.
9. Рекомендуемый стек технологий
Backend: Python (FastAPI или Django) + Celery (для фоновых задач парсинга почты и работы с диском).
Frontend: React.js или Vue.js + TailwindCSS (для быстрой реализации сине-белой дизайн-системы).
База данных: PostgreSQL.
Очереди/Кэш: Redis.
Деплой: Docker + Docker Compose.
10. Критерии приемки (Definition of Done)
Система считается принятой, если успешно проходят следующие сценарии:
На почту отправлено письмо с вложениями -> в системе создан проект, на Диске создана структура папок, файлы скачаны.
Исполнитель А нажимает «Взять в работу» -> Исполнитель Б (с такой же ролью) видит, что задача заблокирована.
Исполнитель А завершает этап -> Исполнитель В (следующий этап) получает уведомление в Telegram и видит задачу в своем «Пуле».
Руководитель нажимает «Отправить клиенту» -> на почту клиента уходит письмо с вложениями/ссылками с Яндекс.Диска.
Интерфейс соответствует сине-белой гамме, логотип из info/logo_tracker_data.png отображается корректно.
